# Part F – Process mining: Solar panel installation (ORG-001)

This folder has the event log for the **solar installation process**, ready to open in **Disco**.

| File | What it is |
| --- | --- |
| `solar_event_log.csv` | The event log for Disco: 500 simulated solar requests, 2,243 events |
| `solar_event_log.xes` | The same log in the standard XES format (Disco, ProM and PM4Py can all read it) |

## 1. The business process

```
Book site assessment ──► Pay deposit ──► Complete site assessment ──► Pay balance ──► Install system
        │                    (or Pay in full)        │                                     ▲
        │                                            ├──► Cancel request (installer: site unsuitable)
        └──► Cancel request ◄────────────────────────┴──► Cancel request (customer) ──► Issue refund (if paid)
```

| Activity | Who does it (resource / role) | In the app |
| --- | --- | --- |
| Book site assessment | NetZero Hub (System) | `POST /api/v1/solar/requests/` |
| Pay deposit (10%) / Pay in full / Pay balance | the customer (Customer) | `POST /api/v1/solar/requests/{ref}/pay/` |
| Complete site assessment | an assessor (Installer staff) | staff status update → `ASSESSED` |
| Install system | an installation crew (Installation crew) | staff status update → `COMPLETED` |
| Cancel request | the customer or the assessor | `.../cancel/` or staff status update → `CANCELLED` |
| Issue refund | NetZero Hub (System) | automatic when a paid request is cancelled |

Business rules:
- The site assessment is free. A deposit must be paid before installation is scheduled.
- The balance is meant to be paid **before** installation.
- Cancelling a paid request always refunds everything paid.
- Status changes follow `SolarRequest.STAFF_TRANSITIONS` (booked → assessed → installed, or cancelled).

## 2. How the event log was generated (process execution)

The app records every step in the `SolarRequestEvent` table with the case (request reference), activity,
timestamp and resource, so the platform produces event logs itself. A few test bookings aren't enough to mine,
so we wrote a **simulation** (`backend/solar/simulation.py`) that executes 500 requests through the same process.
It uses the app's own catalogue, prices, 10% deposit rule and status transition rules.

```bash
cd backend
python3 manage.py simulate_solar --cases 500 --seed 42      # writes the two files in this folder
python3 manage.py export_solar_log                          # exports REAL events recorded by the app
```

The same seed always gives the same log, so the results can be reproduced.

Simulation settings (requests from 5 Jan to 31 Aug 2026):

| Setting | Value |
| --- | --- |
| Installers (share of requests) | Illawarra 40% (3 crews), Harbour City 30% (3 crews), Hunter 15% (2 crews), South Coast 15% (**1 crew, +1 travel day per job**) |
| Payment before the assessment | 50% pay the deposit, 8–20% pay in full, the rest pay nothing yet |
| Cancel before the assessment | 14% if nothing paid, 3% if paid |
| Installer cancels after the assessment (site unsuitable) | 4%, plus 15% for slate/flat roofs and 6% for triple storey |
| Customer cancels after the assessment | 22% if nothing paid, 5% with a deposit, 1.5% if paid in full |
| Battery add-on | 30% of requests; adds 4–14 days waiting for stock |
| Late balance payment (after installation) | 20% of customers who still owe a balance |

Columns in the CSV:

| Column | Use in Disco |
| --- | --- |
| `case_id` | **Case** |
| `activity` | **Activity** |
| `timestamp` | **Timestamp** (pattern `yyyy-MM-dd HH:mm:ss`) |
| `resource` | **Resource** |
| `role`, `installer`, `postcode`, `system_size`, `roof_type`, `storeys`, `battery`, `add_ons`, `total_price`, `amount` | **Other** (attributes, used for filtering) |

## 3. Mining it in Disco (following the Disco Hands-on Tutorial)

These steps follow the 10 steps of the Fluxicon *Hands-on Tutorial* (Process Mining Book 3.1), applied to the
solar process. Take a screenshot at every step marked 📸 for the report.

**Phase 1 – Questions (scoping).** Our three analysis goals, like the tutorial's purchasing example:
1. *Understand the process:* how do solar requests really flow, and how many different paths are there?
2. *Compliance:* is the balance always paid **before** installation, as the payment rule says?
3. *Performance:* target = **installation within 21 days of booking**. How often do we miss it, and where is
   the time lost?

**Phase 2 – Data.** The event log comes from our own platform (`SolarRequestEvent`), generated by simulation
(section 2).

**Step 1 – Inspect data.** Open `solar_event_log.csv` in Excel or Numbers 📸. One row = one event. Case =
`case_id`, activity = `activity`, one timestamp = `timestamp`, plus resource, role and other attributes. These
are the minimum requirements (case ID, activity, timestamp) plus extras for deeper analysis.

**Step 2 – Import data.** In Disco click **Open** and choose the CSV. Set each column 📸:
`case_id` → Case ID, `activity` → Activity, `timestamp` → Timestamp (check that the pattern is
`yyyy-MM-dd HH:mm:ss`), `resource` → Resource, and all others (`role`, `installer`, `battery` …) → Other.
Click **Start import**.

**Step 3 – Inspect process (Map view).** You get the discovered process map: 500 cases, all starting with
*Book site assessment*. Pull the **Activities** slider down to see the main path, then pull **Activities and
Paths** to 100% to see everything 📸. Points for the report: the main flow Book → Pay deposit → Complete site
assessment → Pay balance → Install system, the early ends (dashed lines) after *Cancel request* and *Issue
refund*, and the unexpected arrow **Install system → Pay balance** (75 cases).

**Step 4 – Inspect statistics.** On the **Statistics** tab 📸: 500 cases, 2,243 events, January to September 2026,
about 4.5 events per case. Switch the chart to **Case duration**: the median is about 10 days, but there is a long tail
up to about 51 days.

**Step 5 – Inspect cases (variants).** On the **Cases** tab 📸: **12 variants**. Variant 1 (30.8%) is the happy path.
Note that "Book → Complete site assessment → Cancel request" (8.2%) and "Book → Cancel request" (5.2%) are
common: wasted assessments, like the tutorial's stopped requests. Open one case in **Table** view to show its
full history and attributes.

**Step 6 – Filter on performance.** Filter icon (bottom left) → **Performance filter** → **Case duration**, then move
the left handle to **21 days** 📸. About **67 cases (13%)** miss the target (17% of installed cases). Click
**Copy and filter** and name it "Over 21 days".

**Step 7 – Visualise bottlenecks.** In the "Over 21 days" copy, switch the map to **Performance** and change
*Total duration* to **Mean duration** 📸. The long waits are between *Complete site assessment* and
*Install system* or *Pay balance* (about 15–18 days on average in slow cases, against about 4–6 days overall).
To find the cause, add an **Attribute filter on `installer`** 📸: **South Coast Solar** has 30 of the 67 slow cases,
although it only has 15% of all requests. Its one crew is the bottleneck. A second **Attribute filter on
`battery`** shows that 64% of slow cases include a battery, against 29% overall (waiting for battery stock).

> We only record one timestamp per event, so the activity boxes show no working time. All the time appears on the
> arrows as **waiting time**, which is where the delays really are (just like the tutorial).

**Step 8 – Animate process.** Click **Animation** and press Play. You'll see cases queueing before *Install
system* for South Coast. Mention it in the report (a screenshot of the animation is optional).

**Step 9 – Compliance check.** Go back to the full data set (the drop-down list at the top). In Frequency view,
click the arrow **Install system → Pay balance** 📸 → **Filter this path…** → **Copy and filter** ("Late
balance"). Then open the **Cases** tab 📸: **75 cases** (25% of balance payments) were installed before the
customer paid. This breaks the payment rule and is a cash-flow risk.

**Step 10 – Organisational view.** In the **Project** view, click **Reload**, set `activity` → Other and
`role` → Activity, then import again 📸. The map now shows hand-overs between **System → Customer →
Installer staff → Installation crew → Customer**. The arrow *Installation crew → Customer* (75) is the
same late-balance problem, now seen from the organisation's side.

> **Disco demo version:** the tutorial warns that the demo version has an import limit. If Disco refuses the
> 2,243-event file, ask your lecturer about a Disco academic licence, or make a smaller log with
> `python3 manage.py simulate_solar --cases 100` (and say so in the report).

## 4. What you should find

These figures come from checking the same log with PM4Py, so Disco should show the same numbers.

| Finding | Figure |
| --- | --- |
| Requests that end with an installation | 392 of 500 (78.4%) |
| Requests cancelled | 108 (21.6%); 41 of these were refunded |
| Case duration | median 9.8 days, mean 12.2 days, longest 51 days |
| **Missed 21-day target** | 67 cases (13%); South Coast Solar has 30 of them |
| Variants | 12 |
| Most common path: Book → Pay deposit → Assess → Pay balance → Install | 154 cases (30.8%) |
| **Bottleneck:** median time from assessment to installation | South Coast **15.2 days**, others about **4.2 days** |
| Median time from booking to installation (installed cases) | South Coast 25.2 days, others 10–11 days |
| Battery stock delay: median time from assessment to installation | 14.3 days with a battery, 4.1 days without |
| **Deviation:** balance paid **after** installation | 75 of 303 balance payments (25%) |
| Cancellations by payment before the assessment | nothing paid 37%, deposit 15%, paid in full 7% |

What this means for the business:
1. **Add a second South Coast crew.** It is the main cause of long waits.
2. **Encourage a deposit at booking.** Customers who pay nothing up front cancel about 2.5 times more often.
3. **Enforce or chase the balance before installation** with reminders. A quarter of balances are paid late,
   which is a cash-flow risk.
4. **Keep batteries in stock or order them at booking.** Battery jobs wait about 10 days longer.
